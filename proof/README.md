# Two-colour Zig-Zag Numberlink: the kernel-checked proof

This directory is a self-contained Lake project. It proves that two-colour Zig-Zag Numberlink on
rectangles is decided by `solvableB`, and that the construction `solveZZN` finds a solution
whenever one exists, then gives step-counted versions of the decision procedure and of a
construction with polynomial step bounds. Every certificate is checked by the Lean kernel
(`decide +kernel`), and the results depend only on `propext`, `Classical.choice` and
`Quot.sound`. Its certificate modules and Palomar files are generated by
[`../certgen/regen.sh`](../certgen/regen.sh), which also records how the certificates were made.

## Main results

Prepared for Palomar as two registrations, each a challenge (imports only Mathlib), a solution
and a comparator configuration. They are not yet submitted, and `lake comparator` has not been run
on them; the registered entry, PALOMAR-2026-11-04-000002 v1, states the earlier results:

| Registration | Theorem | File | Statement |
|---|---|---|---|
| Decide (`ChallengeDecide.lean`, `SolutionDecide.lean`, `comparator_decide.json`) | `ZZN.T.solvableBRT_main` | `ZZN/Timed/DecideR.lean` | well-formed `J`: `solvableBRT J` answers `true` exactly when `J` is solvable, within `CdecR · (w h + w + h + 1)` steps |
| | `ZZN.T.fires3T_iff_solvable` | `ZZN/Timed/Main.lean` | both sides ≥ 11, well-formed: the catalogue `fires3T` finds no pattern exactly when `J` is solvable |
| Construct (`ChallengeConstruct.lean`, `SolutionConstruct.lean`, `comparator_construct.json`) | `ZZN.T.solveZ3RT_main` | `ZZN/Timed/RoundTimeR.lean` | every answer of `solveZ3T thinSolveWRT I` is a solution, it returns one when `I` is well-formed and solvable, within `O(M²)` steps, `M = max w h` |

`solvableBRT` runs the catalogue `fires3T` when both sides are at least 11 and the plug DP
algorithm `thinSolveWRT` otherwise; `CdecR = KwR 10 + 300000`, about 9.45 · 10^8. The construction
`solveZ3T thinSolveWRT` deletes blocks of free lines until both sides are at most 37 (or one is at
most 10), solves that instance with the reductions and the plug DP algorithm, and lifts the
solution back. Its bound is
`37 (80 (M+1)² + 400) + (10M+1) KwR 10 + 3 (10M+1)² + 10 + 74 · 700 · 38² + 593 KwR 16 + 3 · 593² + 10`,
about `3.3 · 10³ M² + 9.5 · 10⁹ M + 1.5 · 10¹⁵`.

Also proved, not in a registration:

| Theorem | File | Statement |
|---|---|---|
| `ZZN.solveZ3L_main` | `ZZN/Look/Main.lean` | the construction the libraries run, `solveZ3 (leafL thinSolveW2 tabAll)`: every answer is a solution, and it returns one for every well-formed solvable instance |
| `ZZN.T.solveZ3LT_main` | `ZZN/Look/RoundTimeL.lean` | the same construction with lookup leaves (sides 11–16 answered from the certificates): about `3.3 · 10³ M² + 9.45 · 10⁹ M + 3.5 · 10¹¹` steps |
| `ZZN.solvableB_iff` | `ZZN/Thin/Decide.lean` | every rectangle, well-formed `J`: `solvableB J = true ↔ Solvable J` |
| `ZZN.passes_iff_solvable` | `ZZN/Main.lean` | both sides ≥ 11: `Passes I ↔ Solvable I` |
| `ZZN.solveZZN_sound` | `ZZN/Constr/Main.lean` | an answer `(p, q)` of `solveZZN I` is a solution |
| `ZZN.solveZZN_complete` | `ZZN/Constr/Main.lean` | well-formed and solvable: `solveZZN I` returns an answer |

`solveZ3LT_main` cannot be registered because its statement holds the lookup tables
(`ZZN/LookGen/`, 2.5 MB), over Palomar's 100 KiB limit for a challenge.

## What to read

`ZZN/Statement.lean` (imports only Mathlib) holds the definitions of the plain statements:
- grids and paths (`GridHam`);
- instances and solutions (`Inst`, `IsSolution`, `Solvable`);
- the forbidden-pattern catalogue (`Passes`);
- the plug DP for thin rectangles;
- `solvableB` and `solveZZN`.

The challenges hold, without documentation, the definitions their statements use: from
`ZZN/Statement.lean`, the step-counting definitions in `ZZN/TimedStatement.lean` (`TimeM`,
`fires3T`), and the counted plug DP algorithm and block construction (`ZZN/Timed/ThinRope.lean`,
`ThinRopeCost.lean`, `DecideR.lean`, `RoundT.lean`, `ZZN/Constr/Round.lean`). Everything else is
checked by Lean.

## Building

```bash
lake exe cache get
LEAN_NUM_THREADS=2 lake build
lake env lean Axioms.lean
```

`lake exe cache get` downloads a prebuilt Mathlib. `lake build` builds every library module and
the two solutions. `LEAN_NUM_THREADS=2` keeps Lake to two Lean processes; each needs up to about
13 GB of memory on the certificate modules.

`Axioms.lean` prints the axioms of the main results. Expected: `propext`, `Classical.choice` and
`Quot.sound` only.

A clean build, with Mathlib from the cache, took about 5.4 CPU-hours for the certificates and the
library (2.6 hours of wall-clock time with two Lean processes on a 4-core machine), measured on
2026-11-02. The step-count, construction and lookup modules added since then have not been timed
in a clean build. The Theorem A
certificates take about 3.8 hours, the Theorem B certificates about 0.8 hours.

To judge a registration as Palomar does:

```bash
lake comparator --config comparator_decide.json
lake comparator --config comparator_construct.json
```

## Structure

| Path | Contents |
|---|---|
| `ZZN/`, `GridHam/` | The library: statement, reductions, band extension, Theorem A and B frameworks, plug DP, construction, step counting |
| `BoxKGen/` | Theorem A certificates: 21 boxes `N{W}x{H}` (11 ≤ W ≤ H ≤ 16), 16 477 slices, 255 545 template pairs |
| `WinKU/` | Theorem B certificates: window checkpoints shared by 59 cases |
| `FinalN.lean` | `passes_iff_solvable_K`: Theorem A over the boxes and Theorem B over the windows |
